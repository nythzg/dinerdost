The local calculator has the reference's circular 4×5 keypad, AC, percent, SVG backspace, 00 and a single equals key. Live previews do not save history. Equals promotes the answer and automatically saves the calculation; an operator continues from it and a digit starts a fresh calculation. The demonstrated chain `45×25 = 1,125`, `÷5 = 225`, `−26 = 199` passes. Display grouping does not change stored expressions. Keyboard entry, paste, selection deletion and grouped digit editing remain supported.

Following the user's size correction, the panel is 320px wide with automatic height capped to the viewport. Keys are at most 64px across with 10px gaps; numeric text stays 24px, function text 20px, equals 30px and backspace SVG 22px. Notes and the always-visible Save note button fit in the rendered desktop/phone panel; history scrolls inside it. The subsequent minimal-text request reduces note labels/history buttons to 12px, note text to 13px and history expressions/results to 14px, retaining the numeric keypad sizes.

Notes are optional before or after equals. Equals automatically saves the calculation with a blank note; the always-visible Save note button explicitly attaches or updates the draft note on the same entry. If used before equals, Save note first completes/saves the valid calculation, then attaches the note. Blank/invalid calculations show an error without creating an orphan note. Repeated equals or unchanged note saves do not duplicate entries; a new calculation does not inherit a previously saved note. Account-scoped history survives navigation/reload within its seven-day retention period and supports note editing and confirmed deletion. The server recalculates every newly saved result. Automatic save requests omit draft notes so a changed note cannot break safe retry of an interrupted calculation save.

Relative percentages now give `200+10%=220`, `200-10%=180`, `200×10%=20` and chained `200+10%+10%=242`. The recovered literal-percent rule preserves compound expressions: `200+10%*2=200.2` and `200+(10%)=200.1`. Existing saved results remain unchanged. Original arithmetic limits and unsupported-operation rejection are retained; this does not claim full Android parity or unobserved repeat-equals behavior.

## Seven-day retention · latest direct user request

Calculations and their notes are automatically deleted when their creation timestamp is strictly older than 168 hours, using database time. Updating a note does not restart this period. The exact seven-day boundary is retained until it becomes older. History shows the retention notice and refreshes every minute while open.

Authenticated calculator reads/writes prune only that employee's expired entries inside the tenant's RLS scope. Deferred native applications are rejected first. The local development server also sweeps calculator data across its local database on the first authenticated request and every minute thereafter, without overlapping runs. This removes inactive users' expired entries while the local server runs; after downtime it sweeps again at the next authenticated request. This background writer is explicitly disabled for DATABASE_URL, VERCEL and production configurations. No hosted scheduler or deployment has been added.

Cleanup also removes expression/result/note copies from calculator retry responses, including manually deleted entries. It retains an ID/expired marker and the existing retry fingerprint so replay cannot recreate an expired record; the API returns 410 for an expired calculate replay. Audit events, invoices, payment logs, stock movements/costs and unrelated retry responses are preserved. No schema/migration/dependency change is needed.
